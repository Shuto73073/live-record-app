## 1. サービス概要

音楽ライブ好きのためのライブ情報記録アプリです。自分が観に行ったライブの情報を記録し、一覧にまとめることで思い出として振り返りやすくします。検索機能により、簡単に思い出にアクセスできるようにします。また、記録を集計し自分の体験傾向（どのアーティストが多いか、どの曲が多いか）を分析するためのアプリです。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

音楽ライブに参加する機会が増えていく中で、以下のような感情が生まれたことがきっかけです。

- 過去のライブのことを忘れてしまうので、一覧にまとめて整理したい。
- 今日ライブで聞いたこの曲は、以前いつ・どこで聞いたものかを思い出したい。
- 自分が行っているライブの傾向(どのアーティストが多いか、どの曲が多いか等)を知りたい。
- 好きなアーティストの全楽曲のうち、自分はどの程度ライブで聴くことができているか（以下、コンプリート率）を知りたい

### 2-2. なぜそれが「気になった」のか

元々、記録やコレクションをすることが好きな性分なため。ライブという「推し活」の積み重ねも、記録として残し可視化したいという気持ちがあったため。

---

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

過去のライブの情報を思い出すことができない。SNSやネットで確認しようとしても、そこには他人の投稿や自分が行ったライブ以外の情報も混在しているため、「自分だけの参加記録」として振り返ることができない。

### 3-2. 本当に解決したい課題は何か

- なぜ「自分だけの参加記録」ではないと困る？　→　自分のライブ参加の積み重ねを正確に把握できないから
- なぜ積み重ねを把握できないと困る？ → 　自分のライブの体験傾向が分からず、推し活の達成感・満足感を得られないから
- なぜ達成感を得られないと困る？ → 元々「記録・コレクションすること」自体が好きな性分なのに、それを形にして実感する手段がないから

→ 本当に解決したい課題：自分のライブ参加の記録・コレクションを、ノイズなく正確に積み上げられず、達成感を実感できないこと

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**年齢設定**

- 年齢：20代
- 理由：自分のために使える時間やお金が比較的多く、ライブへ参加する回数も多い年代と推測するため。

**生活・状況設定**

- 生活・状況：頻繁にライブに通っており、特に特定の1〜2アーティストを熱心に追っている。
- 理由：熱心に追っているアーティストがいると、ランキングやコンプリート率などの「積み重ね」を実感する体験が意味を持ちやすいため。

**環境設定**

- 環境：スマホ、PC等
- 理由：ライブ直後など外出先ではスマホ、自宅では個人が入力しやすいデバイス（スマホ、PC等）で記入すると推測するため。

### 4-2. 自分とユーザーの距離

- 自分自身
- 理由：自身がライブに通う中で感じた「記録・コレクションしたい」という思いがそのままアイデアの元になっているため

### 4-3. 実際に使われる可能性について（需要・存在確認）

- まず最初に使ってくれそうな人：自分自身、音楽好きの友人
- このアプリを思い出す場面：ライブが終わった直後、ふと過去の記録を振り返りたい時
- 代わりに使っているもの：Excel、類似アプリ
- それを置き換えてまで使う理由：Excelは入力や管理が面倒で、表示も見にくいため。類似アプリはライブを思い出として振り返る面が強く、ランキングやコンプリート率など、記録を分析的に可視化できる点がないため。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

- きっかけ：ライブに行く回数が増えて、過去のライブの振り返りや体験傾向の分析がしたくなる。
- 最初の一歩：好きなアーティストの登録、参加したライブ情報の入力。
- 継続理由：記録が増えるほどコンプリート率が実感できて楽しいため。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- サービス名：LIVE x LIFE - ライブ参戦記録・セトリ管理
- URL：https://apps.apple.com/jp/app/ライブ参戦記録-live-x-life-/id1629593822
- どんなことができるか：ライブごとにセットリストを記録、メモの追加、ライブ写真の登録、アーティストごとのアルバムジャケット自動表示、テーマカラー/フォントのカスタマイズ、フレンド機能（QRコードで繋がり、参加予定を共有できる）

### 5-2. それでも自分が作りたい理由

実際にLIVE x LIFEを使っていたが、フレンド共有やテーマカスタマイズのようなSNS的・装飾的な機能は自分には不要だった。欲しかったのは自分の体験傾向（どのアーティストが多いか、どの曲が多いか）の分析機能やコレクション要素（コンプリート率の確認）であったため。

### 5-3. 差別化を「体験価値」で表現する

特定のアーティストを熱心に追いかけている人が、ライブを思い出として振り返るだけでなく、ライブに参加するたびに自分の体験傾向やコンプリート率など積み重ねの達成感を実感できるようにするアプリ

---

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：ライブ参加後にすぐアプリで記録する習慣がつく
- 気持ちの変化：「今回のライブではどれだけ聴けたか」を振り返ることで、達成感・満足感を得られるようになる
- 考え方の変化：ライブを「その場で終わるイベント」ではなく、「音楽人生を記録した手帳の１ページ」や「コンプリートに向けて積み重ねていくコレクション」としても捉えられるようになる

### 6-2. 価値を一文で表す

このサービスは、アーティストを熱心に追いかけている人が、自分だけのライブ記録を積み重ね、体験傾向やコンプリート率を振り返ることで、推し活の達成感を実感できるようになるサービス

## 7. このアプリで実現すること

### MVPで作る機能

- アーティスト登録機能
- ライブ情報の登録機能（日付・会場・アーティスト・セットリスト・メモ）
- 記録一覧表示・検索機能
- 分析機能（アーティストランキング、楽曲ランキング、コンプリート率の表示）
- アーティスト楽曲一覧（マスタデータ）登録機能（コンプリート率の算出用）

### 本リリースで作る機能

- UI・体験の改善：コンプリート率やランキングのグラフ化による可視化強化
- 入力補助（曲名のサジェスト/自動補完）
- セットリスト画像からの自動読み込み（OCR）
- 外部API連携による楽曲一覧データの自動取得
- 写真添付機能など

## 8. このアプリの懸念点とその対策

### 懸念点①：入力の手間

- 何が問題になりそうか：ライブ記録やセットリストの入力に手間がかかり、継続して使われなくなる可能性がある
- なぜそう思うか：実際にExcelで管理していた際も入力の煩雑さが課題であったため、アプリでも同じ課題が起こりうる
- そのために考えている対策：MVPではシンプルな入力フォームに絞ってリリースし、本リリースで入力補助（サジェスト/自動補完）やセットリスト画像の自動読み込み（OCR）を実装して手間を削減する

### 懸念点②：モチベーションの維持

- 何が問題になりそうか：個人で記録をつけるだけのアプリのため、記録すること自体が一時的な熱で終わり、使われなくなる可能性がある
- なぜそう思うか：使い続ける動機が自分の満足感に依存するため
- そのために考えている対策：コンプリート率やランキングなど、記録が増えるほど可視化される要素をMVPから用意し、記録を続けること自体に楽しさを持たせる

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：Ruby on Rails
- DB：PostgreSQL
- デプロイ先：Render
- 使用予定ライブラリ：TailwindCSS+DaisyUI、Devise（本リリース時）、Pagy

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | カリキュラムで学習済みであり、限られた期間内で現実的にアプリを完成させられる選択だと判断。 |
| React / Next.js | 不採用 | 学習コストが高く、限られた開発期間ではキャッチアップが難しいと判断 |
| Hotwire（turbo, stimulus） | 採用 | Railsを中心とした構成を維持したまま、画面全体をJavascriptで書き換える必要なく画面の体験を向上させるため。 |
| TailwindCSS + DaisyUI | 採用 | ユーティリティクラスの組み合わせで実装でき、デザインの自由度の高さにより手が止まることを避けられる。DaisyUIで完成済みのUIパーツを使えるため、UI実装の負担を抑えられる |
| Bootstrap | 不採用 | 完成済みコンポーネントで手軽だが、独自のJavaScriptで画面制御を行うため、Hotwire（Stimulus）と制御が競合する可能性がある |
| has_secure_password | 採用 (MVP時) | Rails標準機能（bcrypt）のみで、必要最小限の認証（登録・ログイン）をシンプルに実装できる。MVPでは、パスワードリセット等の機能は不要と判断 |
| Devise | 採用（本リリース時） | パスワードリセット等、認証機能を拡充する段階ではDeviseの機能の豊富さが活きるため |
| Pagy | 採用 | 記録一覧のページネーションに必要。軽量・高速でメンテナンスが活発なため。 |

- 今回チャレンジしたい点：Hotwire（Turbo/Stimulus）を使った動的なUIの実装
- 不安な点：TailwindCSS・DaisyUIを使ったフロントエンド実装、およびHotwire（Turbo/Stimulus）の実装経験が浅く、画面の動きをどこまでTurbo/Stimulusで実現できるか、どこからカスタムJSが必要になるかの見極めに時間がかかる可能性がある

### 10-3. キャッチアップ不足の懸念

キャッチアップ不足の段階では以下の懸念点があります。

1. **完成までのハードルが高い**：使用する技術のキャッチアップにかかる時間には個人差があり、一定の時間を要することが予想される
2. **Issueの見積もりが難しい**：どこまで理解していて、何が分からないのか、調査にかかる時間が不明瞭な場合、開発期間内に完了することが難しくなる

今回、特にキャッチアップに不安があるのはTailwindCSS・DaisyUIを使ったフロントエンド実装と、Hotwire（Turbo/Stimulus）による画面の動的な制御です。実装を進める中でどうしても難しい場合は、UIの複雑さを下げる方向で調整し、無理に高度な実装を目指さないようにします。
